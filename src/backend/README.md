# Backend abstraction (draft)

Seam for the cross-vendor (Vulkan compute) backend. The engine layer
(`Engine*.cpp`) is already torch-free and calls kernels only through the
launch functions exported via `/*[AutoHeaderGeneratorExport]*/` markers, all
aggregated today by `EngineState.h`. This directory makes that implicit
boundary explicit:

```
Engine*.cpp  ──►  backend/api/*.h          (launch declarations, generated)
                  backend/api/BackendRuntime.h  (memcpy/memset/alloc/events)
                        │
        ┌───────────────┴───────────────┐
  backend/cuda/                    backend/vulkan/
  (existing src/kernels/**,             (SPIR-V pipeline dispatch over a
   unchanged, stays canonical)      VulkanGSPipeline-style device layer)
        │                                │
        └────────► backend/common/SortScan.h ◄────────┘
                   (CUB on CUDA / onesweep radix sort + prefix-sum on Vulkan)
```

## Layout

- `api/` — the backend-neutral surface the engine sees.
  - `Projection.h`, `Rasterization.h`, `TileIntersect.h`, `PixelWise.h`,
    `Optimizer.h`, `Densify.h`, `Loss.h`, `Background.h`, `Bilagrid.h`,
    `Visualizer.h` — **generated forwarders**
    (`tools/codegen/generate_backend_api.py`) that group the per-kernel
    launch headers per subsystem. The AUTHORITATIVE declarations and types
    live in the per-kernel `.cuh` headers (declaration sections generated by
    `generate_headers.py`), which are CUDA-include-free and parse under
    `-DSS_BACKEND_VULKAN` without the CUDA toolkit. Forwarding (not
    copying) keeps one definition of every preamble type — a TU may include
    a module header and an individual `.cuh` together without ODR issues.
  - `BackendTypes.h` — portable CUDA-layout vector types + empty
    `__device__`/`__host__` macros for non-CUDA builds.
  - `BackendRuntime.h` — the device runtime surface the engine layer uses
    (audited: memcpy sync/async all directions, memset, malloc/free, pinned
    host alloc, events, device/stream sync).
  - `RenderTypes.h` — forwarder to the authoritative render-output types in
    `Primitive.cuh`.
- `common/SortScan.h` — sort/scan/select primitives shared by backend
  implementations (below the API; the engine never calls it).
- `cuda/`, `vulkan/` — implementations (not yet created; see wiring below).

## Wiring steps (in order, each independently buildable)

1. **Header portability pass** — DONE (2026-07). `Tensor.h` routes all host
   cuda* calls through `BackendRuntime.h` (its `__device__` method bodies
   were already `__CUDACC__`-guarded); `Common.cuh` / `NonShQuantState.h`
   swapped their CUDA includes for `BackendTypes.h` (`GradQuant.cuh`,
   `PoolSlots.h`, `Primitive.cuh` needed no change). The whole chain —
   these headers plus every generated `api/*.h` — parses as C++17 with
   `-DSS_BACKEND_VULKAN` and NO CUDA toolkit on the include path.
   `CUB_WRAPPER` remains in `Common.cuh` (macro, only expanded in `.cu`);
   it migrates to `common/SortScan.h` with step 5.
2. **Engine runtime calls** — DONE (2026-07). All direct `cuda*` calls in
   the engine layer AND the app layer (`TrainerCore`, `RenderWorker`) now go
   through `backend::` (~90 token rewrites across 19 files; zero behavior
   change — the CUDA implementations are inline cudart wrappers). Notes:
   - `backend::Stream` IS `cudaStream_t` under the CUDA backend
     (forward-declared `CUstream_st*`), so launcher declarations in
     `BilagridBindings.h`/`EngineInternal.h` use `backend::Stream` while
     their `.cu` definitions keep `cudaStream_t` — same type, no casts.
   - `backend::is_device_pointer()` replaces the `cudaPointerGetAttributes`
     probes (`EngineCommon.h`, `Camera.h`).
   - `backend::last_error()` (cudaGetLastError semantics) preserves the
     viewer worker's graceful-failure checks.
   - `TrainerCore`'s driver-version preflight is intentionally CUDA-only
     behind `#ifndef SS_BACKEND_VULKAN`; the Vulkan backend adds device
     enumeration at the same call site.
3. **Portable launch headers** — DONE (2026-07). Instead of re-pointing
   `EngineState.h`/`Engine.h`/`ext.cpp` at new headers (which would have
   duplicated preamble types → ODR errors in `.cu` TUs), the per-kernel
   `.cuh` headers themselves went CUDA-include-free (16 include swaps;
   `_kernel.cuh` device headers untouched). Acceptance: `EngineState.h`,
   `Engine.h`, `EngineCommon.h`, `EngineInternal.h`, and all `api/*.h`
   parse with `-DSS_BACKEND_VULKAN`, no CUDA include path. Also fixed a
   pre-existing include-order fragility (`EngineInternal.h` now includes
   `PixelWise.cuh` for `PPISPRegLossIndex` explicitly) and made the
   `batch_quantile_masked_radix_select` template return portable `int`
   (was `cudaError_t`; both call sites ignore it).
4. **CMake** — DONE (2026-07). `SS_BACKEND=cuda|vulkan` (default cuda).
   `cuda` builds exactly as before (CUDA language enabled after the option
   check). `vulkan` is a compile-check stage: builds the `csrc_portable`
   OBJECT library — every engine/host `.cpp` (all 22 TUs) with
   `SS_BACKEND_VULKAN`, no CUDA toolkit required — and stops before any
   executable. It becomes a real build as backend/vulkan/ fills in (step 5).
5. **backend/vulkan/** implements `BackendRuntime.h`, `SortScan.h`, then the
   api modules kernel-by-kernel (Slang `-target spirv` entry points reusing
   the existing `src/shaders/*.slang` device functions), in the phase order:
   projection → SH/background → tile intersect + sort → rasterization fwd →
   visualizer, then training (losses, backward, optimizer, densify).

## Not covered by the generated API (hand-written headers, port separately)

`Meshing.h` / `MeshingRaster.h`, `BilagridBindings.h` (sample / TV-loss /
fused-Adam family), `Quantile`, `ColorShiftReg`, `RasterizationMomentsFwd`
(no export markers), `CheckpointIO.h`, `DataManager.h`, plus the
engine-internal exports in `EngineColorSpace.cpp`. Same portability rules
apply; they join `api/` once marker-annotated or manually mirrored.

## Known porting risks (flagged early on purpose)

- **64-bit sort keys** (DECIDED 2026-07): tile intersection sorts `int64`
  keys with `int32` values (`cub::DoubleBuffer<int64_t>` in
  `IntersectTile.cu`). The Vulkan sort must support 64-bit keys — 32-bit
  packing only holds for Mip-NeRF-360-sized scenes and overflows on
  large-scale real-world datasets. Extend the vendored onesweep sort to
  wide keys (or hi/lo double-sort), using `begin_bit`/`end_bit` to skip
  passes the key range doesn't need.
- **Device addressing**: `BackendRuntime.h` keeps plain-pointer semantics,
  which on Vulkan presumes `VK_KHR_buffer_device_address` (core 1.2,
  MoltenVK-supported) over a suballocated pool. The buffer+offset fallback
  would ripple through `Tensor.h` — avoid unless a target platform forces it.
- **Float atomics**: ~1,069 `atomicAdd(float)` sites; fine on NVIDIA/AMD via
  `VK_EXT_shader_atomic_float`, absent under MoltenVK/Metal → CAS-loop
  emulation behind a capability macro (VkSplat's `USE_EMULATED_F32_ATOMIC`
  pattern), selected per-device at pipeline-variant compile time.
- **Subgroup width**: shuffle/ballot code must not assume 32 lanes (AMD
  wave64); use Slang `WaveActive*` and size-agnostic reductions.
