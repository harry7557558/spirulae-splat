# Localization

Spirula Studio's interface exists in thirteen languages: English, Japanese,
Simplified and Traditional Chinese, Korean, German, French, Spanish,
Portuguese, Italian, Dutch, Russian and Turkish.

This page is for **shipping** a localized build. For how the mechanism works
and how to write or add translations, read `src/i18n/README.md`; it is the
reference and this is the operations manual.

## Build options

| option | default | what it does |
|---|---|---|
| `SS_DEFAULT_LANG` | `en` | the language used when nothing else is detected |
| `SS_FONT_CJK` | `fetch` | how the **full** CJK faces reach the user |

`SS_FONT_CJK` does **not** decide whether the interface renders in Japanese,
Korean or Chinese. It always does, in every build: the four subset faces in
`assets/fonts/` are embedded unconditionally. See *Fonts* below.

Neither is a list this file maintains: `cmake/SsOptions.cmake` reads the
language set out of `src/i18n/Languages.h`, so `-DSS_DEFAULT_LANG=xx` with an
unknown `xx` fails at configure time with the valid values printed.

```bash
# the default: English fallback, CJK fonts fetched on demand
./build_develop.bash -DSS_BUILD_GUI=ON

# a Simplified-Chinese build that works offline
./build_develop.bash -DSS_BUILD_GUI=ON -DSS_DEFAULT_LANG=zh_hans -DSS_FONT_CJK=sc

# a build that must never touch the network for fonts
./build_develop.bash -DSS_BUILD_GUI=ON -DSS_FONT_CJK=none
```

`SS_DEFAULT_LANG` is the *last* step of the resolution chain, not an override:
`--lang`, `SS_LANG`, the settings file and the OS locale all come first. It is
what a headless run, a container with no `LANG`, or a stripped Windows
environment lands on. That is why it is a language rather than a hard-coded
`en` — a build shipped as `-DSS_DEFAULT_LANG=ja` must come up Japanese there.

## Fonts

Five faces are **embedded in every build**, 507 KB together:

| file | size | covers |
|---|---|---|
| `SpirulaUI-Regular.ttf` | 58 KB | Latin + Cyrillic, from Source Sans 3 |
| `SpirulaCJK-{JP,SC,TC,KR}.otf` | 449 KB | the ~600 characters *per region* this program's own translations use, from Noto Sans CJK |

That is what makes a default build render all thirteen languages, in the right
regional glyph forms, with nothing to download. It matters most in the language
picker, which is exactly the screen a user who cannot read the current
interface language has arrived at — a download button there is a request to
read something they came to that menu because they could not read.

Subsetting is what makes it affordable. A full Noto Sans CJK face is 4–8 MB and
there are four of them, because **Han unification** gives the shared codepoints
different default glyph forms per region; a Japanese reader shown the
Simplified Chinese face gets kanji in Chinese forms, which is legible and
visibly wrong. Cutting each one down to the characters the catalogs actually
contain costs ~110 KB, so all four fit and nobody gets the wrong forms.

Alternatives measured and rejected: one pan-CJK subset is 287 KB, saving 135 KB
but rendering 262 shared characters in Simplified Chinese forms for three of
the four languages; delta-encoding the four against a common base lands at
358 KB, because of the shared characters only about half have identical
outlines across the regional cuts.

The atlas merges the base face, then the full regional face if one has been
fetched, then all four subsets with the **current language's region first** —
first source wins per codepoint, so the current language gets its own forms
while the other three still supply what only they have (hangul exists only in
the KR face, the simplified 简 of 简体中文 only in SC).

### Keeping the subsets in sync

The subsets are generated from the catalogs, so editing a translation can
outgrow them, and the symptom is one hollow box mid-sentence. Two tools:

```bash
python3 tools/make_ui_font.py            # rebuild all five (needs fonttools + network)
python3 tools/check_font_coverage.py     # fail if a catalog outgrew them
```

The check runs on every `build_develop.bash`. It needs no network and no
fontTools — it parses `cmap` by hand — so it is cheap enough to live there.

### `SS_FONT_CJK` — the *full* faces

The full faces are still worth having, for a much smaller job than they used
to do: dataset paths, file names and typed mask prompts are user data and can
hold any character at all, which no subset of our own strings can anticipate.

| value | what ships | user experience |
|---|---|---|
| `fetch` *(default)* | one self-contained executable | the interface is complete already; the picker offers the full face for file names, with the size shown |
| `none` | one self-contained executable | same, minus the offer; CJK **file names** may show boxes |
| `sc` \| `tc` \| `jp` \| `kr` | executable + `fonts/<face>.otf` beside it | full coverage offline in that region |
| `all` | executable + all four faces (~23 MB) | full coverage offline everywhere |

The full faces are **bundled, not embedded**, and deliberately:
`ss_embed_file()` turns one byte into five characters of C source, so `all`
would be a 130 MB array literal. A regional build installs a `fonts/` directory
next to the executable, which is the first place `src/app/gui/Fonts.cpp`
looks.

## Where fonts are looked for

In order:

1. `$SS_FONT_DIR` — a full path, for testing and for a user with their own copy
2. `<exe dir>/fonts/` — what a regional build ships
3. `<cache dir>/fonts/` — what a download writes

Every candidate is checked by size **and** SHA-256 against
`assets/fonts/cjk_faces.txt` before it is handed to the rasterizer; a font is
parsed by stb_truetype, which is not something to feed unverified bytes off the
network. The hashes are pinned to a commit, not a branch, so they cannot go
stale under us.

A face already on disk is loaded **whatever the interface language is**, not
only for CJK locales: an English UI still has to draw a dataset path like
`C:\写真\` without turning it into boxes.

## The state of the translations

`bash tools/check_i18n.sh` prints the remaining work, and there is currently
none: **all 1738 messages carry all thirteen languages.** That covers the home
screen, the trainer, the status strip, the modals, the viewport, the config
editor, the file dialog, the New Dataset screen, the external-COLMAP *Advanced*
panel, saved presets, batch training, masking, the mask preview, the model
catalogue and the licence consent — plus every training flag's name and help
(`src/i18n/catalog/TrainFields.h`, one pair per row of `SS_CONFIG_FIELDS`), the
presets, the navigation modes, the projection and lens models, and the log
lines and stage names this program writes itself.

**The command line is included, and so is everything a run prints.** That is
the part worth being explicit about, because it is the part that is easy to
miss: a GUI has a language picker, and a terminal does not.

| where it comes from | catalog |
|---|---|
| `spirula --help`, `spirula train --help`, and the lines a training run prints | `catalog/Cli.h` |
| `spirula sfm` — every stage, count and warning of a reconstruction | `catalog/Sfm.h`, through `src/sfm/core/Log.h` |
| `spirula mesh` — every stage, count and warning of a meshing run, and its `--help` | `catalog/Mesh.h`, through `src/mesh/MeshLog.h` |
| `spirula sam` — the device table, the per-frame line, the summaries | `catalog/Cli.h` |
| `spirula sfm --help` — 120 flag descriptions and 9 group headings | `catalog/SfmFields.h` |
| `spirula sfm --help` — the command summaries, descriptions and labels, and `ba` | `catalog/SfmHelp.h` |
| `spirula sam --help` and `spirula sam extract --help` | `catalog/SamHelp.h` |
| reading a dataset: the COLMAP, Nerfstudio and Metashape parsers, and the image loader | `catalog/Data.h` |
| what a GUI job says while it runs, and what it says when it fails | `catalog/Log.h` |

The GUI shows a terminal panel, and `spirula sfm` and `spirula mesh` run inside
it as child processes, launched with `--lang`. So those two translate
themselves, and what a user sees in that panel is their own language from top
to bottom — not our stage names in Japanese around English counts.

### Wrapping a help page

Help text is stored **one string per paragraph** and wrapped at print time by
`i18n::wrap()`, never by hand. Two reasons, and the second is the one that
matters: it measures in terminal columns rather than bytes, so a CJK line is
not twice as long as it looks — and it breaks BETWEEN CHARACTERS where a
language has no spaces to break at. Chinese and Japanese are written without
spaces; a `find(' ')` wrapper leaves them as one line four hundred columns
wide. It also refuses to start a line with the closing punctuation or small
kana that may not open one.

The flag column is laid out with `i18n::pad_to()` for the same reason. Where a
translated flag description no longer fits beside its flag, the flag gets its
own line rather than pushing the column out.

### Reading a translated child process back

The GUI's mesh progress bar has to understand what the child printed, and the
child is now printing Japanese. Matching on English fragments is exactly the
thing that breaks the moment a tool is translated, so it matches on the
**message** instead: `i18n::scan()` is the inverse of `i18n::format()` — give it
the same `Msg` the child printed with and the line it printed, and it hands back
what stood in the `{0}`, `{1}` positions.

```cpp
std::vector<std::string> got;
if (i18n::scan(msg::mesh::cameras_rendered, tail, got))   // "cameras rendered: 12/120"
    frac = atof(got[0].c_str()) / atof(got[1].c_str());
```

`src/app/gui/MeshRunner.cpp` uses it for both numbers it needs, and compares the
stage against the very `msg::mesh::stage_*` entries `MeshLog` printed. Nothing
in that protocol is English, so nothing in it breaks when a translation is
edited.

Deliberately **not** translated, and each for a reason:

| what | why |
|---|---|
| mask prompts and their placeholder examples | SAM 3's text encoder reads English; a translated example is advice to type something that works worse. See `src/app/gui/MaskPrompt.h` — the palette is how a non-English speaker still writes a good prompt. |
| third-party child-process output (COLMAP, ffmpeg) | not ours to rewrite, and it is what a bug report is pasted from. `spirula sfm` and `spirula mesh` are *ours*, so they **are** translated |
| COLMAP / config parameter names inside a translated sentence | `Mapper.abs_pose_min_num_inliers` is what the reader types into COLMAP and searches its docs for. The prose around it is translated; the identifier never is |
| preset names, camera-model identifiers, lens-model names, flag names, format names | command-line and file-format vocabulary; the picker shows a translated label *and* the name |
| machine-readable output: `spirula sam`'s detection TSV, the codec table | a script reads these, and a script does not have a language |
| deep diagnostics: `SS_SFM_MAP_PROF`, `--check` / `--audit`, `SS_MESH_DEBUG_RENDER`, the seam and focal-curve dumps, the GPU profilers, the self-test binaries | read by whoever is debugging the pipeline, not by whoever is waiting for a result |
| `src/core/Env.h`'s `SSPLAT_*` deprecation notice | that header is deliberately dependency-free — the standalone tool binaries include it and link neither the engine nor `ss_i18n` — and the sentence is about the spelling of an environment variable |
| language names in the picker | someone looking for their own language is looking for the word they call it by |

### Review status

The translations were produced in one pass by the author of the code, not by
native speakers, and they should be read as a solid first draft rather than as
shipped copy. Two groups need human review before a release:

1. **ja / zh-Hans / zh-Hant / ko / de** — the languages where a bad string is
   most visible, and where the terminology (splat, primitive, bundle
   adjustment) has established conventions this pass has guessed at.
2. **Every message attached to something irreversible or legal** — overwriting
   a reconstruction, the stop-training confirmation, and the whole model
   licence block. These are marked with a comment in the catalog. A licence
   summary that softens or overstates somebody else's terms is worse than no
   translation, and machine or single-author translation is not acceptable for
   them.

The catalogs are plain C++ headers, so a reviewer needs no tooling: edit the
string, rebuild, and the compiler checks that nothing was dropped.

## Testing a language without changing your system

```bash
SS_LANG=ja ./build/spirula            # environment
./build/spirula --lang zh-Hant        # command line, on any subcommand
./build/spirula --help                # lists the codes
```

`--lang` is consumed in `src/app/Main.cpp` and removed from `argv`, so it works
in front of any tool and no per-tool parser knows about it.
